従来の「文書全体を一括でLLMに投げる」方式は、構造が崩れやすく、編集方針の細かな制御が難しいという課題があった。
しかし、**Markdown→AST**で分解し、**ノード単位で変換**して最後に構造を**再合成**すれば、次の要件を同時に満たせる。

* **Structureの保存**：DOM的に扱えるため機械可読。書式崩れを防ぐ。
* **Semanticsの再構成**：文体・トーン・用語統一・翻訳などの高次タスクをLLMに任せる。
* **並列化**：ノードごとに処理するため**スループット向上**と**部分的なやり直し**が容易。

## コア概念

### 1) 不変条件（構造を守るためのルール）

* 見出しレベル（`#`の数）は**変更禁止**。
* 箇条書き・番号付きリストの**階層と順序**は維持。
* リンクURL、脚注ID、画像パスは**不変**（テキストのみ編集可）。
* コードブロックとインラインコードは**非編集**。
* 表の**列数と行数**は固定（セル内テキストのみ編集）。
* 参照（見出しアンカー、脚注、図表番号）は**壊さない**。
* フロントマター（YAML/TOML）は**読み取り専用**。
* 空行と改行規則は**ラウンドトリップ可能**に保つ。
* 非ASCII記号の使い方（全角・半角など）は**方針で統一**。

### 2) ノード単位のプロンプト設計

各ノードに役割（heading/paragraph/listItem/blockquote/tableCellなど）を付与し、**役割別テンプレート**を適用する。

* **見出し**：「意味は保持、より簡潔に」「名詞句で」「絵文字禁止」
* **段落**：「冗長さを15% 削減」「専門用語は英語併記」「敬体/常体の統一」
* **リスト**：「各項目は1文30–60字」「文頭体言止め禁止」
* **引用**：「引用符内は原文保持、前後の説明だけ整える」
* **表セル**：「名詞の揺れ禁止、単位を明示（ms, MB, %）」

### 3) 並列化と一貫性

* ノードは**依存関係グラフ**（例：見出し → その節の段落 → 参照）でスケジューリング。
* まず**文書サマリ**と**用語集（glossary）**を生成 → 各ノードプロンプトに添付し、**語彙とトーン**を固定。
* 再合成後に **Consistency Pass**（別のLLMでもよい）で、**固有名詞・数値・参照整合**を締める。

## 具体的な実装例（TypeScript／Unified 生态系）

> 主要ライブラリの一例：`remark-parse`（Markdown→MDAST）、`unist`（AST ユーティリティ）、`remark-stringify`（AST→Markdown）

```ts
import { unified } from 'unified';
import remarkParse from 'remark-parse';
import remarkStringify from 'remark-stringify';
import { visit } from 'unist-util-visit';

// 1) 解析
const ast = unified().use(remarkParse).parse(markdown);

// 2) ノード収集とID付与
let i = 0;
visit(ast, (node: any) => { node._id = `n${i++}`; });

// 3) ドキュメントサマリ & 用語集
const { summary, glossary } = await llmPlan(ast);

// 4) ノード別プロンプト生成
const jobs = [];
visit(ast, (node: any, _idx, parent: any) => {
  if (shouldEdit(node)) {
    const prompt = buildPrompt({ node, parent, summary, glossary });
    jobs.push({ id: node._id, role: node.type, prompt });
  }
});

// 5) 並列実行（ワーカー/レート制御は省略）
const results = await Promise.all(jobs.map(runLLM));

// 6) AST 更新
const byId = new Map(results.map(r => [r.id, r.text]));
visit(ast, (node: any) => {
  if (byId.has(node._id)) applyNodeEdit(node, byId.get(node._id));
});

// 7) 整合性パス（参照/用語/数値）
await consistencyPass(ast, { glossary });

// 8) 再出力
const out = await unified().use(remarkStringify, { bullet: '-', fences: true }).stringify(ast);
```

要点は次のとおり。

* `shouldEdit()`で**コード・リンクURL・脚注ID**を除外する。
* `buildPrompt()`は**役割別テンプレート**と**不変条件**（禁止事項）を明示する。
* `consistencyPass()`で**用語揺れ・数値桁区切り・単位**を正規化する。
* 失敗時は**ノード単位のロールバック**が可能。

## プロンプト設計テンプレート（抜粋）

**共通前置き（system相当）**

```
あなたは構造を厳密に保持する編集者です。
- コード、URL、脚注ID、見出しレベル、テーブル形状は変更禁止。
- 句読点と単位表記を標準化し、冗長さを15%削減。
- 出力はプレーンテキストのみ。Markdownの外形は呼び出し側が付与します。
```

**段落（paragraph）用**

```
役割: 本文段落
目的: 読みやすさの改善（敬体）。専門用語は英語併記。
文脈サマリ: {{summary}}
用語集: {{glossary}}
入力: {{node.text}}

制約:
- 箇条書きに変換しない。
- 文末は「です・ます」で統一。
- 数値は半角、単位はSI記号。

出力: 改稿後の本文のみ。
```

**見出し（heading）用**

```
役割: 見出し。
目的: 5～12語で簡潔化。キーワード保持。
入力: {{node.text}}
制約: 文末記号と絵文字は禁止。品詞は名詞句。
出力: 見出しテキストのみ。
```

## 長文翻訳ワークフロー（構造保持）

1. **AST 化 → ノード分割**
2. **グロス生成**（訳語対照、固有名詞、製品名）
3. **ノード並列翻訳**（表セルはセル単位、リンクはテキストのみ）
4. **再合成**（元の見出し・リスト階層を復元）
5. **整合性パス**（訳語統一、数値・単位、参照の生存確認）
6. **機械可読評価**（後述のAST差分・構造検証）

**メリット**

* 目次、脚注、表、リンクが**崩れない**。
* **再実行コストが小さい**（一部だけ再翻訳）。
* 品質を**ノード属性に応じて最適化**（例: 見出しは凝縮、本文は自然さ重視）。

## 校正・スタイル変換

* トーンプリセットではacademic/casual/business/marketingなどを用意する。
* ノードロールに応じて**句読点・文末・敬語**を切り替える。
* 安全策として、引用は原文を保持し、再叙述は避ける。コードには触れない。
* 文体差分は`original.md`と`styled.md`の**AST構造差分**で比較する（構造一致は合格）。

---

## 整合性パス（Consistency Pass）の中身

* 用語辞書を適用し、同義語を正規語に吸着する（例: LLM/大規模言語モデル）。
* 数値の一貫性を確保する（百分率と小数、桁区切り、SI単位）。
* 参照の健全性を検査する（見出しアンカー、脚注、表番号、リンク疎通）。
* リズムを調整し、文長のばらつきを平準化して段落間の重複を除去する。

---

## 並列化・コスト・SLO設計

### スケジューリング

* **BFS**で上位見出しから順に計画し、同一セクションを**バッチ化**する。
* 依存（図表→本文参照）を**DAG**で表現し、**ワーカー**に配賦する。

### コスト近似

* トークンコストは `Σ node_i (prompt_i + output_i)`に近似する。
* 速度は `max(depth) + Σ(batch_j / 并行度)`に近似する。
* キャッシュはノードの**ハッシュ（内容+役割+設定）**で再利用する。

### 障害時のふるまい

* 構文検証NGの場合は、該当ノードだけ再試行するか原文にフォールバックする。
* レート制限時は、優先度キューで見出しと概要を先行させる。

---

## 検証と自動テスト

1. **AST 構造同型性**：ノード種別・階層・順序・参照IDが一致
2. **不変条件チェック**：URL/コード/脚注/表形状の不変更
3. **スタイル検査**：句読点・文末・単位・表記ゆれ
4. **意味評価（用途別）**
   * 翻訳: COMET/BLEUなどと人手スポットチェック。
   * 校正: 可読性指標（文長、品詞比率）。
5. **スナップショットテスト**: 小さな差分をPRで可視化。

---

## ユースケース（拡張）

* 多言語ブログは、英語版と日本語版に**構造単位**で更新差分を適用する。
* 技術ドキュメントは、Markdown→HTML/Notion/PDFへ変換し、ASTベースで自然言語部分のみ再構成する。
* チーム内ドキュメントは、役割別プリセットで**ビジネス調**へ統一する。
* AIライティング支援では、**部分リライト・要約・注釈付け**をノード単位で自動化する。

---

## よくある落とし穴と対策

* 番号付きリストの再採番は、レンダラに任せず**値を固定**するか連番を検証する。
* 脚注と見出しアンカーの衝突は、IDレジストリで**一意性を保証**する。
* 表の崩れは、セル内改行とパイプ`|`のエスケープを徹底する。
* 引用の意図変化は、引用本文を**原文固定**とし、前後の解説のみ編集する。
* 画像代替テキストは、URLを不変とし**altだけ**改善する（長さ制限）。
* フロントマター破損は、専用ノードとして分離し、出力を禁止する。

---

## セキュリティ・プライバシー

* PIIや秘匿情報は、変換前に正規表現とルールベースで除去する。
* プロンプト漏洩対策は、ノード最小文脈と必要情報のみを添付する方針とする。
* 監査ログは、ノードID、入力ハッシュ、出力ハッシュ、担当ワーカーを記録する。

## 従来手法との比較

| 観点         | 一括変換（従来）  | ASTノード並列（本手法）    |
| ------------ | ----------------- | -------------------------- |
| 構造保持     | 壊れやすい        | **強い**（不変条件で制御） |
| 品質の安定   | 文脈次第で揺れ    | **役割別テンプレ**で安定   |
| 再実行コスト | 全文再生成        | **部分差し替え**で低コスト |
| スループット | 低（長文1ジョブ） | **高（並列）**             |
| 観測可能性   | 粗い              | **ノード粒度の監査**       |

## ロードマップ（発展）

* 差分パッチ生成は、AST差分からPRを自動生成する。
* 整合性の制約充足は、用語集（glossary）、数値、参照を**制約ソルバ**で厳密化する。
* 表現制御は、RAGで社内用語集やスタイルガイドを動的参照する。
* 文書間整合は、多言語版どうしで**双方向整合**（同一IDを共有）とする。

## まとめ

**Markdown×AST×LLM**は、テキスト生成を「構文的に制御可能」な粒度まで分解し、**構造（Structure）と意味（Semantics）の両立**を実現します。
翻訳、校正、スタイル変換、フォーマット変換といった現場要件に対し、**構造を守りながら文体や内容を変える**ことを、**安全・高速・再現性**のある形で提供できます。これが**文章エンジニアリング**の出発点です。
